# 08 · 测量规范：三层阶梯 + 四件套 + 窗口规则

## 8.0 三层测量阶梯（先选层级，再设计实验）★

> **核心规则：能用低层级回答的问题，绝不上升层级。带数字的结论必须标注层级（L1 / L2 / L3）。**

| 层级 | 工具 | 特征 | 能回答 | 结构上答不了 |
|---|---|---|---|---|
| **L1 算力层** | `llama-bench`（**单进程多值**） | 噪声最低，一个进程扫完 N 组 | 线程 / 批大小 / KV 类型 / flash-attn / 加载模式；卸载档**速度排序**；深度掉速；**多模型 A/B**；单请求端到端 | 显存与溢出；投机解码；模板与采样；能力与质量 |
| **L2 物理层** | `llama-server` + 四件套 + 分段 prefill | 每点一次模型加载，同会话 A/B 可比 | 装得下 / 能用 / 好用三级判定；投机解码；思考预算；真实模板与采样 | 质量是否损伤；token 精确计数 |
| **L3 质量层** | `llama-perplexity`（KL / PPL）→ 能力题库 | 客观、长跑 | KV 量化 / 卸载 / 量化档对**质量**的损伤 | 速度与显存 |

### 层级规则（写结论前先自检）

1. **不上升层级**：先问"L1 能不能答"；只有 L1 只能给线索的（卸载档、上下文上限）才进 L2；
   只有"质量有没有坏"才进 L3。
2. **L1 必须单进程多值**（把候选值写成逗号列表，一个进程扫完）。
   **禁止**用"每个取值重启一次 server"下带幅度的结论——那样单点噪声会大到把真实增益淹没。
3. **L1 不报显存**：卸载档与上下文上限的最终判定必须回 L2 看 `shared`。
   L1 看得出**严重**溢出（速度断崖），看不出**轻微**溢出。
4. **L1 没有 `-tb`**：提示词处理线程由 L1 的 `pp` 曲线峰值推断，或回 L2 做 A/B。
5. **跨表引用必须标层级**：L3 类的存档值只能当方向、不能当幅度；**禁止用 L3 数据下 L1 级结论**。
6. **L1 参数是全局笛卡尔积**：多个多值参数会组合展开（不是配对）。
   多模型同时指定时，**无法给每个模型各自不同的卸载档**——要么取对两者都有效的公共档
   （= "同卸载深度"对比），要么对每个模型单独扫出各自的最优。
7. **L1 已知坑**：
   ① 上下文**不能**用某个独立参数表达，只能由"提示词长度 + 生成长度 + 深度"组合表达；
   ② **`pp` 的噪声显著大于 `tg`** → prefill 结论必须多重复；
   ③ 自动内存适配机制（如 `--fit` 一类）**不能替代显式卸载扫档**——不传卸载参数时它可能仍按全量权重估算；
   ④ "端到端聚合"行的数值随提示词/生成混合比变化，**引用必须写清混合比**。

### 工具矩阵：要回答什么 → 第一选择 → 交叉验证 → 判定门

| 要回答的问题 | 第一选择（层级） | 交叉验证 | 判定门 |
|---|---|---|---|
| 线程 / 批大小 / KV 类型 / flash-attn 的最优 | `llama-bench` 多值扫（L1） | L2 端到端复核 | 有 CPU 卸载才扫线程（`06-threads.md`） |
| 卸载档位 | `llama-bench` 速度排序（L1） | **L2 `shared`（必需，硬信号）** | 权重 + KV 超显存（`02-offload.md`） |
| 装得下多少 ctx | 先算账（L1.5） | L2 逐点 `shared` | 需要 > 32K 上下文 |
| 能用多深 / 好用吗 | L2 **分段 prefill** + 该深度 decode | L1 深度掉速 | 同上 |
| 投机解码收益 | L2 专项（`07-speculative.md`） | — | GPU 有空闲且 `--help` 支持 |
| KV 量化档怎么选 | `llama-perplexity --kl-divergence`（L3） | 能力题（回答"变了要紧吗"） | 想上更激进档时才扫（`03-kv-quant.md`） |

> **工具准入标准（唯一标准：能不能加速"推断最优参数"）**：
> 只有能**减少到达最优参数集所需 GPU 时间**的工具才进本 skill。
> 与单实例参数搜索无关的（多槽容量类）、既不加速搜索也判不出目标量的（某些整体质量指标）、
> 以及属于"造模型"环节的（量化 / 重要性矩阵类）**一律不进**。

## 8.1 四件套采集

> **每个测试点都必须同时记录四件套**：
> `t/s` + 显存（`dedicated` / **`shared`**）+ GPU 利用率 + CPU 占用率，**外加**生成 / prefill 分解。
> 单一指标无法判定瓶颈。

### ★ 窗口规则：先声明相位 → 再设计窗口 → 最后校验占比

1. **声明相位**：这条结论属于 **decode 相**还是 **prefill 相**？
2. **设计窗口**：窗口必须由该相位主导。
   - decode 相 = **极短 prompt + 长生成**（生成足够长，保证窗口由生成主导）
   - prefill 相 = 深填充
3. **校验占比**：被测相位耗时须占窗口的绝大部分（例如 ≥80%）。
   **反例**：把利用率采样器套在一次深填充请求上，则该窗口测到的是 prefill 画像，
   与"decode 期瓶颈"的结论方向可能完全相反。
4. **采样时机**：时钟 / 功耗等必须在**请求进行中**采样；请求返回后再采 = 已回落空闲 = **无效值**。

### 各项采集口径

| 指标 | 口径 |
|---|---|
| 生成 t/s | 取服务端返回的 `predicted_per_second`；每点 ≥2 次取稳态（**首个请求含图捕获，弃用**）；**报速度必须注明生成长度** |
| prefill | `prompt_per_second` + `prompt_n` + `prompt_ms` + **总墙钟 = prompt_ms + predicted_ms**；记录完整 `timings` 而非只取 predicted |
| 显存 | `Dedicated` / `Shared` 计数（多卡按目标卡过滤）。**`shared` 跳升 = KV / 编码器溢出（物理信号）** |
| GPU 利用率 | `nvidia-smi` 轮询，取生成阶段**尾部**均值。阈值判据：高于高水位 = GPU-bound；低于低水位 = 瓶颈在别处 |
| CPU 占用率 | ★ 用 **`cores_busy` = 进程 CPU 时间增量 ÷ 墙钟**（得到"用了几核"）。**不要只信瞬时百分比** |

### 无效数据自检（命中任一即标无效，不进均值）

- `cores_busy` 与 CPU 百分比**自相矛盾**
- 功耗 / 时钟在请求**之后**采集
- 生成提前 EOS 导致窗口过短
- 首个请求未弃用（含图捕获）
- **你说不出这条读数属于哪个相位**

## 8.2 阶段 A：吞吐扫描（稳定填充）

- 测试 prompt 用多轮对话填充（user 短问 + assistant 长答），**结尾必须是问题**——纯重复文本会直接触发 EOS。
- **前缀复用陷阱**：连续请求共享前缀时，`prompt_n` 是**增量**，而 eval t/s 仍是**全深度**的速度；两者口径不同，不要混算。
- **填充配深**：按"每对问答的 token 数"估算需要几对，再**按取整反推档位**。
  分档常常略微超出目标（因为要向上取整），这是**取整**造成的，不是估算误差——报告里要说明。
  "每对多少 token"用本机语料实测一次即可。

## 8.3 harness 缺陷清单（命中即"测量缺陷"，不得记成模型特性）

| 症状 | 根因 | 修法 |
|---|---|---|
| 中文提示词题得分异常低 | 生产者输出经 shell 重定向被按**本地代码页**解码 → 中文变替换字符 → **损坏的 prompt 真的发给了模型** | **由生产者直接以 UTF-8 写文件**；禁止经 shell 重定向转手；核对发出前的 prompt 字节 |
| 编程题 0%（模型其实答对） | 多个代码块被**拼接**成一个文件（同名符号互相覆盖） | **拆块后每块单独判分取最高**；`max_tokens` 给足 |
| 脚本启动即失败（参数无法转换） | 形参名撞上 shell 的**自动变量** | 形参改名 |
| 日志里只有脚本原文、没有输出 | 重定向包住了**脚本块对象**而没有调用它 | 显式调用脚本块 |
| 后台作业的输出拿不到 | 作业完成后输出缓冲被清空 | **一律同时落盘**，再从文件读 |
| 判定正则误杀正确回答 | 模型用不同语言 / 换行 / 不同编号作答，未命中正则 | 判分前人工核对判定正则；正则覆盖多语言与格式变体 |
| 输出的中文/emoji 报编码错 | 控制台代码页无法表示该字符 | 在程序内显式把标准输出重配置为 UTF-8 |
| 题目"变简单了"却无人察觉 | 答案键本身有缺陷（见 `09-capability-bank.md` 验键） | 建库时验键 |

> **这些缺陷有一个共同解药：对照组**——把基线模型用**同一套 harness** 跑一遍。
> 没有对照组，就会把测量缺陷报成模型的能力短板。规则见 `10-reliability.md`。

## 8.4 进程与脚本规范

- 服务端必须以后台作业方式启动，且**清理要显式 kill + 验证端口已释放**，不留脏状态。
- Windows 上用 PowerShell 7（不要用 5.1：UTF-8 无 BOM 的中文脚本会被按本地代码页解析）。
- 每完成一步就落盘（原始日志 + 结构化结果），不要把结论留在内存里。
