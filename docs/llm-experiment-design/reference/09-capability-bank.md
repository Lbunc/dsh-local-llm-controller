# 09 · 阶段 B：能力验证（第 3.4 步）

定档后验证两件事：

1. **模型的能力水平**（用于标注上限与共享盲区）
2. **关键参数变更是否损伤能力**（KV 量化 / 卸载档 / 思考预算）

> **能力题输出长度不定，不得混进吞吐测量**——否则破坏 t/s 的可重复性。

## 9.2 `max_tokens` 的算法

按 `05-reasoning-budget.md` 的硬规则：

```
max_tokens = rb(= n_ctx/2) + 答案余量
夹取：prompt_tokens + max_tokens ≤ n_ctx
```

- 长上下文题的 prompt 很长 → 可用输出预算被挤压，**先 `/tokenize` 量真实 token 数**（`04-context.md` ④）。
- **`--reasoning-budget` 不是硬截断** → 长思考题会被"**输出预算**"而非"思考预算"卡死。

---

## 9.3 截断与中断的处理（两条硬规则）

### ① 截断记 `truncated`，重跑，**不得判 0**

判分器逻辑：

```
if (判分不通过 and finish == length)  -> state = truncated（"未产出"）
```

- 从**分母剔除**，不进正确数，也**不算答错**。
- 原因：无法知道截断前它是否会答对。
- 处置：**加大 `max_tokens` 重跑该题**。
- 例外：若判分**通过**，说明答案在被截断前已经完整 → 正常计分。

### ② 中断/补跑：**只补跑未完成的题，不整轮重跑**

- 用 `-Only <题号列表>` 原地合并进已有答案 JSON。
- 合并逻辑必须**既替换已有、又追加原本没有的题号**（只替换会静默丢结果）。
- 已完成的题**从逐题日志还原**，不要为了拿回数据重跑模型：

```
python scripts/recover_bank_json.py --logs "<WorkDir>/logs" --bank bank/10q_hard.json --out-dir "<WorkDir>/data"
```

逐题日志已包含还原所需的一切：`finish` / `prompt_n` / `gen` / `wall` / `tps` / 思考链 / 正文。

## 9.4 区分度门与"区分度轴复现检验"

### ① 先过区分度门

跑基线模型（对照组）后：

- **全对** 或 **全 0** → 本库对该代模型**无区分度** → 结论只能写「**测不出差异**」，**不得排名次**。
- 得分差很小但非零 → 逐题看差异落在哪些题、属于哪个轴（**不要只看总分**）。
- 报告给**逐题得分表**，不要只给平均分（平均值会掩盖"互补失败"）。

### ② ★★ n=1 不许下结论：区分度轴复现检验

主库只跑出**少数（尤其只有 1 道）**差异题时，**既不能直接说"谁更强"，也不要整轮重跑**。做法：

1. **定位那个轴**（差异题考察的能力方向，例如"约束满足"）。
2. **只在该轴上追加若干同难度题**：
   - 来自**互不共享解的同源实例**（不同基础网格 / 不同题面），不要用同一实例的不同小问充数；
   - **难度同档**（用可比的规模/线索数量等指标对齐）；
   - 主库**保持冻结不动**，复现库**独立记分**。
3. **合并主库的差异题 + 复现题**，按"同轴连胜 / 0 胜"判定该差异是否成立。
   复现次数要足以排除偶然（判据来自 `10-reliability.md`：非预期差距需重复多次才算）。
4. 复现检验同样要**两个模型都跑**（它也是对照组的一部分），不能只测一边。

> **★轴上的"成本画像"往往比正确率更有信息量**：
> 记录该轴上各题的**生成长度**与**墙钟**。若某模型在该轴上的生成长度
> **全部贴近 `max_tokens` 上限且方差极小**、而正确率仍低，说明它
> **不是"不会做"，而是"做不出来还停不下来"（缺收敛判据）**。
> 这是一种可报告的部署缺陷：这类任务必须靠 `max_tokens` 强制熔断，否则单请求延迟不可控。
> 进一步地，**"生成长度与题目难度不相关"本身就是一条值得报告的缺陷信号**。

### ③ 报告口径

- 差异题少时，写清"n 是多少"，不要用 n=1 下排名结论。
- 若某轴经复现成立，写清该轴的**样本数**与**双方成绩**，并说明该结论只覆盖这个轴。

## 9.5 ★★ 建库必做"答案键验证"

> 困难题库最大的风险不是模型不行，而是**题目 / 答案键本身是坏的**。
> 那会把**源数据缺陷**直接报成"模型能力不足"。

**可靠度从高到低**：

1. **自己穷举 / 复算**（最可靠）：能枚举的题就枚举，能独立推导的就推导，与公布键比对。
2. **两个独立镜像互校**：同题在不同来源的键是否一致。
3. **官方仓库原键**：直接用官方发布的数据集答案字段。

**★必须检查题面自洽性（反例类别）**：

若题面本身**无解或与答案不符**，则该条目的答案**无意义**，必须弃用换题。典型可查的自洽性检查：

- **不变量检查**：题目里的操作是否保持某个量（和、个数、奇偶性）不变？目标要求是否与该不变量矛盾？
- **量级检查**：答案是否落在题目约束的范围内（例如要求整数答案且不超过某上界）？
- **单位 / 定义检查**：题面用到的术语与答案的口径是否一致。

**若不做这一步会发生什么**：两个模型都会在这道坏题上"双双失败"，
于是报告会写成"两模型都栽在这道题上"——**而实际上这道题谁也做不出来**。

**换题记录必写进题库的 `note` 字段**：原题来源、为何判定为缺陷、换成哪道、新键如何验证。

## 9.6 判分必须程序化

- 规则 / test cases / JSON 比对 / 数值精确匹配，**禁止主观打分与手写标准答案**。
- 编程题：**拆代码块后每块单独判分取最高**（避免多块拼接互相覆盖）；
  若官方公开用例过少（例如只有题面样例），应补充**独立参考实现生成的用例**，
  且参考实现**必须先对全部官方用例验证一致**才可用于生成。
- harness 缺陷清单见 `08-measurement.md` 8.3。
- **必须跑对照组**（`10-reliability.md`）。
