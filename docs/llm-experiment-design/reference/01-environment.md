# 01 · 环境与基线（第 1 步）

## 1a. 部署约束（固定，写进所有脚本）

这些是**约定常量**，不是测出来的值；所有实验必须一致，否则结果不可比。

| 项 | 取值 | 理由 |
|---|---|---|
| 端口 | 固定单一端口 | 测试前确认占用该端口的服务已停；**测完必须释放**，否则后续服务起不来 |
| apiKey | 留空（server 不传 `--api-key`） | 本地测试不校验；客户端仍统一发一个固定 header，便于与正式接口保持同形 |
| 采样 / 惩罚 | `--temp 0.6 --top-k 20 --top-p 0.95 --min-p 0.0 --repeat-penalty 1 --presence-penalty 0` | 固定下来，避免采样差异污染对比 |
| 思考预算 | `--reasoning-budget = n_ctx / 2` | **硬规则**，见 `05-reasoning-budget.md` |
| 最小上下文 | `n_ctx ≥ 32768`；上下文扫描起点 32768 | 低于此没有代表性 |
| 单实例 | `-np 1`；不扫 `--parallel` / `--cont-batching` | 本流程是单实例参数搜索，KV 池可激进吃满 |
| 监控 | 带 `--slots --metrics` | 四件套与投机接受率需要 |

## 1b. 硬件清单

一次记全，后续所有报告引用同一份：

- GPU：显存总量、当前占用（多卡按目标卡过滤）
- CPU：物理核数 / 逻辑核数
- llama.cpp：版本与 commit
- 系统：OS 版本、驱动 / CUDA 版本

## 1c. 基线流程

1. **关后台**：请用户关闭浏览器等占显存 / 占 CPU 的程序。
   后台负载会**同时**污染显存读数与 t/s，是最常见的错误来源。
2. **加载验证**：确认服务端报告的 `n_ctx` 与 chat template 符合预期；发一次短请求确认对话通路正常。
3. **记录干净环境基线**：基线上下文下的短生成稳态 t/s + **空闲 shared 显存** + 空闲 CPU 占用。
   后续每个实验点都相对这个基线判断（尤其 `shared`，见 `02-offload.md`）。

> **基线是"物理信号"的比较基准**。没有基线，就无法判断某个点是否发生了溢出——因为溢出的表现是"shared 相对基线跳升"，而不是某个绝对数值。

## 1d. 视觉模型：两个必问项

当 `00-probe.md` 的 `hasVision` 命中时，**必须依次问用户，不得自行决定**：

1. **「这次要不要做视觉测试？」**
   - **不做** → **明确不加载 mmproj**，纯文本测量。否则投影器白占显存，污染速度与"最大可用上下文"两个结论。
   - **要做** → 进入第 2 问。
2. **「mmproj 卸载到 GPU 还是 CPU？」**
   - **GPU**：`--mmproj-offload`（通常默认启用），设备跟随 `--device` / `-mmdev`。
   - **CPU**：`--no-mmproj-offload`（或 `-mmdev none`）——把投影器留在 CPU，**省显存给 KV**，代价是图像编码变慢。
   - **必须记录选择**：投影器是实打实的显存占用，会改变能撑的上下文长度 → 结论必须标注"含 / 不含视觉编码器"。

做视觉测试时一并记录：

- `--image-min-tokens` / `--image-max-tokens`：动态分辨率模型每张图的 token 上下限，**直接决定 prefill 成本**
- `--mtmd-batch-max-tokens`：图像批处理上限

> 视觉分支的结论与纯文本分支**不可混用**：两者的显存占用与 prefill 成本结构不同。
