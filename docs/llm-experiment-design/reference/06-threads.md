# 06 · CPU 线程（第 2.5 步）

判定门：**仅当有权重或专家被卸载到 CPU 时才扫**（全 GPU 时线程数无关，跳过）。

## 6.1 理论值：先从上游取证，不要猜

按 `00-probe.md` 0d 取证：

| 取证对象 | 方式 |
|---|---|
| 上游 auto | `llama-bench.exe -h` 中 `-t` 的 `(default: X)` |
| server 实际取值 | 不传 `-t` 启动 server，读日志中的线程初始化行 |
| 硬件拓扑 | CPU 的**物理核数**与**逻辑核数**（分别读出，不要混用） |

**常见反直觉点**：上游 auto 的 `-t` 语义可能不是"逻辑核数"，而是**物理核数**。
不要假设，取证后再用。

**机制解释**（为什么物理核数更可能是对的起点）：

- 推理的逐算子之间存在 barrier 同步；
- 超线程兄弟核共享向量 / FP 执行单元，多出来的线程只增加争用；
- 混合核（性能核 + 能效核）架构上，barrier 会被最慢的线程拖住。

→ 因此**逻辑核数往往是错的起点**，物理核数是更合理的理论值。

**但理论值不等于答案**：必须实测。实测峰与 auto 不一致时以实测为准，并把差异写进报告。

## 6.2 测法：必须用 L1 单进程多值

```
llama-bench.exe -m <model> -t 10,12,13,14,15,16,18,20 -r 3 -p 512 -n 512
```

- **一个进程扫完所有取值**（这是 L1 的核心优势，见 `08-measurement.md`）。
- **禁止**用"每个取值重启一次 server"下带**幅度**的结论：那样单点噪声会大到把真实增益淹没或误报。

**曲线判据**：

1. 峰值应落在**物理核数**附近；若明显偏离，检查是否有其他瓶颈（内存带宽、显存溢出）。
2. 低端看能效核是否在参与（若 CPU 是混合核架构，可对比"只用性能核"与"用全部物理核"）。
3. **报速度必须注明生成长度**（短生成的数值受图捕获热度影响，不能与稳态值混用）。

## 6.3 `-tb` 不必单独扫（默认做法）

- `-tb` 默认等于 `-t`（帮助文档即如此）。
- 提示词处理线程的最优点可由 L1 的 `pp` 曲线峰值推断；若 `pp` 与 `tg` 峰值同点，保持 `-tb = -t` 即可。
- 只有需要拆分证据时才回 L2 做 A/B。

## 6.4 判据：CPU 是不是瓶颈

- **CPU 接近饱和且 t/s 不再上升** → CPU 是瓶颈。
- **CPU 未满** → 瓶颈在别处，结合 GPU 利用率与 `shared` 判断（`08-measurement.md`）。
- CPU 用量口径：用"进程 CPU 时间增量 ÷ 墙钟"（核数），**不要只信瞬时百分比**（见 `08-measurement.md` 无效数据自检）。
