判定门：**GPU 有空闲**（利用率未饱和）**且**本机 `--help` 支持对应的投机参数，才扫。
GPU 已饱和时投机解码结构上无收益；不支持则跳过。

## 2.6 ★ 探测到 MTP 就必须做"带 MTP"的测试

`00-probe.md` 的 `hasMTP` 命中（存在 `blk.*.nextn.*` 张量）时：

- **不能只交无 MTP 的基线**——MTP / draft 正是这类模型的主要吞吐手段；
- 必须把「**无 MTP vs 带 MTP**」列为**同会话配对 A/B**（唯一变量 = 是否开启投机），而不是可选优化。

## 2.6 ★ 开测前必须询问用户：draft 的 KV 量化档

参数：`-ctkd / --spec-draft-type-k`、`-ctvd / --spec-draft-type-v`（取值同 `-ctk`，出厂默认可能比主 KV 更宽）。

**为什么必须问**：draft 缓存**额外占显存**，选得过宽可能：

- 直接把卸载档挤爆，或
- 把刚腾出的显存余量吃回去（与 `-ncffn` 救援冲突，`02-offload.md`）

→ **这一项会改变"哪个配置能用"**，属于必须由用户决定的部署取舍。问清 draft KV 档后，再定 `n-max`。

## 3.3 专项测量：除四件套外必须额外记录

| # | 必须记录 | 口径 / 判据 |
|---|---|---|
| 1 | **接受率** | 从 `/metrics` 取"接受 tokens / draft tokens"；**需要先定一个阈值**（高则值得深挖，低则无收益），阈值按本机与模型设定并写明 |
| 2 | **GPU 利用率** | 原理是"draft 便宜 + 验证批量分摊"——**GPU 必须有空闲才有收益**；已饱和则必无效 |
| 3 | **显存增量** | 对比开 / 关投机时的**空闲 ded**；draft 缓存是实打实的占用 |
| 4 | **开关对照** | 关键结论**重复 ≥3 次**，不能只报一次 |
| 5 | **n-max 扫描** | `n-max` 全部候选都要扫（接受率随 n 衰减），不要只测一个值 |
| 6 | **draft KV 量化档** | 开测前问用户；并记录该档带来的 draft 缓存显存增量 |
| 7 | **存在性对照** | 模型有 MTP 时，必须给出"无 MTP vs 带 MTP"的同会话配对结果，**不能只报一个数** |

## 3.3a 与显存救援的关系（互斥）

投机解码需要额外显存，`-ncffn` 救援需要腾出显存。**两者在显存紧张时只能选一个**：

- 救援场景（大上下文已溢出）→ 选**纯 `-ncffn`**，不开投机；
- 全 GPU 且有显存余量 → 开投机。

判定依据仍是 `shared`（硬信号）：开了投机后若 `shared` 相对基线跳升，说明余量已被吃回。
