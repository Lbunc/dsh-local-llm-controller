# 05 · 思考预算（第 2.4 步）★ 硬规则：`-rb = -c / 2`

判定门：`00-probe.md` 的 `has_thinking` 命中（chat template 含思考开关）才适用；无思考模式直接跳过。

## 5.1 硬规则（唯一取值公式）

```
--reasoning-budget = n_ctx / 2
```

| `-c` | `-rb` |
|---|---|
| 32768 | 16384 |
| 65536 | 32768 |
| 131072 | 65536 |

**理由**：思考预算必须**随上下文窗口缩放**，而不是取固定值。

- 固定的小值在小上下文下勉强够用，在大上下文下等于把一个巨大的可用空间闲置；
- `n_ctx / 2` 的含义是「**思考吃一半、提示词与答案吃另一半**」，与 `04-context.md` 的上下文三问同源；
- 每档上下文都按此公式取值，**不要为某个模型单独调**（除非有实测理由并写进报告）。

> 用 **server 启动参数**传，不要用请求级参数：请求级的 budget 常被客户端忽略。

## 5.2 `-rb` 是"思考上限"，不是"输出上限"

客户端 `max_tokens` **必须单独设置**：

```
max_tokens = rb + 答案余量
```

| 题目类型 | 答案余量（经验起点，可按实测调整） |
|---|---|
| 数学 / 长推理 | rb + 8k 量级 |
| 选择 / 短答 | rb + 4k 量级 |

再做一次夹取：

```
prompt_tokens + max_tokens ≤ n_ctx
```

- 长上下文题**必须先 `/tokenize` 量真实 prompt token 数**再定 `max_tokens`（`04-context.md` ④）。
- 若 prompt 很长，可用输出预算被挤压 → 这类题的 `rb` 实际用不满是正常的，**不要为此调低 `rb`**。

## 5.3 ★★ `-rb` 不会硬截断（重要）

`--reasoning-budget` **不是**硬性刹车：思考超过预算后模型仍可能继续思考。

推论（必须写进结论与脚本逻辑）：

1. **把 `rb` 设小并不会"省时间"**，只会让你误以为预算在起作用——真正卡住答案的永远是 `max_tokens`。
2. **截断一律记 `truncated`（"未产出"），从分母剔除，并重跑（加大 `max_tokens`）**；
   **不得判 0 分**——因为无法知道截断前它是否会答对。
3. 若某题在合理的大预算下仍不收敛，应作为**模型行为特征**记录（例如"缺收敛判据、长度与题目难度不相关"），
   而不是当作答错。

## 5.4 无预算时的翻车形态

不设 `rb`（或设得过小）时，复杂题会把 `max_tokens` 全部吃在思考里，导致：

- `finish_reason = length`
- 正文为空或只有半句

**这属于 harness 配置问题，不是模型能力问题。** 排查顺序：先看 `finish_reason`，再看思考长度与 `max_tokens` 的关系。
