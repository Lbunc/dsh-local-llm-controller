# 测试项目共同经验（跨模型通用测量教训）

> **来源**：本轮 occamy 测试中的测量缺陷，**适用于所有后续模型文档**。
> **合并规则**：后续模型文档如遇到相同章节，统一移至此文档合并，避免重复记录。
> **每条记录**均为通用方法教训，不绑定特定模型；模型相关的特定发现在各模型文档的对应章节中说明。

## §1 采样窗口污染

| # | 现象 | 根因 | 修正 |
|---|---|---|---|
| 1 | 首轮四件套 `cpu=12-26%` 与直测 `cores_busy=17.7` 矛盾 | util 采样窗口被**prefill 主导**（decode 仅占 5% 窗口） | 改「短 prompt + 1500 tokens 长生成」 |
| 11 | 短测扫描 idle shared 382–404 MiB 且随 ctx 不涨 | 残留 server 进程与桌面占用污染 | 深填充复测 131072 = 235 MiB；**该表作废，仅留作勘误记录** |
| 16 | 短测 idle shared 判定「可容纳」会误判 | 短测单点 idle shared 受残留进程/基线漂移污染，不随 KV 增长 | **用深填充 idle shared 序列判定**；扫描脚本每点应按端口杀进程再取值 |
| 12 | `sm_clk` / `power` 列 | 在请求返回后才采样（GPU 已回落空闲） | **无效列，勿引用** |

> **通用教训**：
> - **decode 相四件套**必须用「短 prompt + 长生成」让窗口由 decode 主导，否则测到的是 prefill 画像。
> - **idle shared 判定必须采用深填充序列**，不可使用短测单点（短测 idle shared 会被残留进程/基线漂移污染，且不随 KV 增长）。
> - **性能类指标**（sm_clk / power）需与计算忙期同步采样，否则测到的是回落空闲值。
> - **扫描脚本每点应按端口杀进程再取值**，避免残留进程污染。

## §2 脚本与编码缺陷

| # | 现象 | 根因 | 修正 |
|---|---|---|---|
| 2 | c2 多约束题 50%、c4 多跳聚合 16%/0% | Python→pwsh `>` 重定向按 GBK 解码 stdout，**JSON 中文全变 U+FFFD → 提示词被损坏** | 由 Python 自己写 UTF-8 文件（`-o`）；重跑后两者均 100% |
| 3 | c3 编程题代码块判分全失败 | ① 所有 ``` 代码块被**拼接**成一个文件（同名函数互相覆盖）；② 6144/8192 token 预算**截断** | 拆块后**每块单独判分取最高**，`maxtok` 提到 10240；重跑后两者均 89% |
| 4 | cowork 循环全部 `Cannot convert System.Object[] to Hashtable` | 形参名 `$args` 撞 PowerShell **自动变量** | 改名 `$targs`；重跑后两者 2/2 |
| 5 | 一次日志只有脚本原文、无输出 | `{ ... } *>&1 \| Tee-Object` 只**输出脚本块对象**而非调用它，须写 `& { ... }` | 加 `&`；同时避免依赖 job_output（作业完成后会被清空） |

> **通用教训**：
> - **中文 stdout 必须用 UTF-8 写文件**，禁止 `>` 重定向（GBK 解码会损坏 JSON）。
> - **代码块判分**需拆块独立后取最高，避免同名函数覆盖 + token 截断。
> - **PowerShell 形参**避免使用 `$args`（自动变量），改用 `$targs` 等。
> - **Tee-Object 必须配合 `& { ... }`** 调用脚本块，否则只输出对象不执行。
> - **job_output 作业完成后被清空**，日志收集不可使用其结果。

## §3 测量方法论

| # | 现象 | 根因 | 修正 |
|---|---|---|---|
| 8 | 结论「甜点 = `-t 12~16` 平台区，+5~8%」幅度偏保守 | 用「每点重启一次 server = 一个独立作业」逐点测 → 单点跨作业噪声 ±7%，只能保守表述 | 改用**单进程 `llama-bench`（±0.04）**复测：**峰值精确落在 `-t 14`，+18.8%** |
| 10 | 同为 q8_0「健康档」prefill，实测出现 719.5 pps 与 611.2 pps 两个数值 | 前者 `ncmoe 20 @32K ctx`，后者 `ncmoe 22 @128K ctx`（多 2 层专家在 CPU + compute buffer 随 ctx 增长） | 两者都对；**引用 prefill 数值必须带 (ncmoe, ctx, 深度)** |
| 14 | `-ncmoe` 扫描中最优档短测 t/s 可能不是最高 | 短生成窗口由 decode 主导不充分，高 ncmoe 档短测 t/s 偏高而深填充 eval 降级 | **以 idle shared 物理信号判定最优档**，短测 t/s 仅作辅助参考 |
| 15 | 全量深填充是 all-or-nothing（只能得「超时」，得不到拐点） | 单点深填充无法定位 pps 拐点 | 改为按 ~26K tokens 分档加深、每档记录增量 prefill 的 pps / prompt_ms / 墙钟 / idle shared，pps 掉到 <300 即判「不可用」并停止 |
| 17 | `llama-fit-params` 四项和低估实际显存占用 | 其四项和（model + KV + compute + rs）**不含 CUDA context + 桌面占用** | 实测约 **+670 MiB**，用 fit-params 估算余量时务必预留 |

> **通用教训**：
> - **单点跨作业噪声约 ±7%**，保守表述与精确表述需区分场景（平台区 vs 尖峰）。
> - **单进程 `llama-bench`** 可精确到 ±0.04，适合定位精确最优值；多作业重启适合验证稳定性。
> - **引用 prefill 数值必须带 (ncmoe, ctx, 深度)** 三要素，否则跨表不可比。
> - **`-ncmoe` 必须当变量外推**，不能把单点结论当成模型极限。
> - **短测 t/s 存在误导风险**：高 ncmoe 档短生成 t/s 可能更高，而深填充 eval 会降级；**idle shared 是唯一可靠的溢出物理信号**，判定最优档必须以它为准。
> - **全量深填充是 all-or-nothing**（只能得「超时」，得不到拐点）；定位 pps 拐点要用**分段加深法**（~26K tokens 一档，记录增量 prefill 的 pps / prompt_ms / 墙钟 / idle shared，pps <300 即停）。
> - **`llama-fit-params` 四项和不含 CUDA context + 桌面占用**（实测约 670 MiB），用其估算显存余量时务必预留这部分，否则会高估。

## §4 MoE 卸载断崖规律

| # | 现象 | 根因 | 修正 |
|---|---|---|---|
| 13 | `-ncmoe` 卸载扫描中，decode 速度在 19↔20 档之间出现断崖式下跌 | MoE 专家权重未完全卸载到 CPU，GPU 显存不足导致专家计算回退 | 以 **idle shared** 物理信号（而非 t/s 短测）判定最优档；断崖档号在同尺寸 MoE 模型间可迁移 |

> **通用教训**：
> - **MoE 模型 `-ncmoe` 卸载扫描必现断崖**（decode 速骤降 + idle shared 跳升），断崖档号与模型权重尺寸强相关。
> - **同尺寸 MoE 模型的断崖档号一致**（如 18.42 GB 的 occamy 与 Uncensored-IQ4_NL 均在 19↔20 断崖），可作为新模型 `-ncmoe` 初筛参考。
> - **断崖上方（ncmoe 偏小）短测 t/s 可能更高**，而深填充 eval 会降级；**idle shared 是唯一可靠的溢出物理信号**。详见 **§3 #14**。
> - 本条与 §3「短测会骗人」同源，只是场景从「卸载档选择」扩展到「MoE 断崖档号预测」。

## §5 本机硬件 decode 特性（通用，非模型决定）

> **本机结论**：本轮测试的 decode 相表现由宿主机硬件决定，与模型无关。i5-13600KF + RTX 4070 SUPER 12GB 上观测到：
> - **decode 阶段是 CPU-bound**：GPU util 47-54%（约一半算力闲置），CPU 100% 饱和（20/20 逻辑核），GPU 功耗 102.8W（远离 220W 功耗墙）。
> - **`-t` 最优值 = 物理核数 14**（非逻辑核 20）：`llama.cpp` 默认 `n_threads = 物理核数`，超线程兄弟核共享向量/FP 单元，多出的线程只增加 barrier 与争用。实测 `-t` 超过物理核数后 decode 速度下降（20 = −15.8%，22 = −24.6%）。
> - **建议**：显式指定 `-t = 14`（物理核数），`-tb` 保持 `= -t`。此结论适用于本机所有模型。

## §6 数据完整性说明

> - **跨会话负载漂移 ±10-15%**：不同会话测得的同类数值在此范围内波动属正常，跨表对比以同会话内部对比为准。
> - **先查存档再补测**：执行新测试前，先查存档有没有同条件点（ctx/KV/ncmoe/线程都一致）；有则直接引用并标注「存档值」，只补测新增点。

## §7 视觉预设部署通用经验

> **适用范围**：所有使用 Qwen-VL 系投影器（`mmproj`）且将投影器置于 CPU 的模型。以下为跨模型通用的部署经验，不绑定特定模型。

| # | 经验 | 说明 |
|---|---|---|
| 1 | `--image-min-tokens` 必加 | 上游 `load_hparams` 对 Qwen-VL 系有明确警告：grounding 任务低于 1024 会出错。实测模型会打印此警告，加 `--image-min-tokens 1024` 消除 |
| 2 | 投影器置于 CPU = 零显存成本 | `-mmdev none`（或 `--no-mmproj-offload`）使投影器权重以 compute buffer 形式分配在 CPU，显存占用 ≈ 0 MiB。置于 GPU 的代价 ≈ 1100 MiB（含运行时开销），远大于文件本身 |
| 3 | 视觉额外成本只在首次编码新图 | 首图 1048 tokens 编码约 14.7s（一次性代价，非 decode 速度）；同图重发走 KV 前缀复用，编码降到 111–120ms |
| 4 | 逐 token 生成速度与纯文本相同 | 投影器不参与逐 token 生成，视觉预设的稳态 decode t/s 与纯文本预设比值 ≈ 1.00（差 0.3%，在噪声内） |
| 5 | 思考预算按硬规则 `-rb = n_ctx/2` | 128K ⇒ 65536；256K ⇒ 131072。`max_tokens` 需另算（`-rb` 非硬截断），并满足 `prompt + max_tokens ≤ n_ctx` |
| 6 | 文本预设参数可原样照搬到视觉预设 | KV q8_0 buffer、compute buffer、模型 buffer 与纯文本逐位相同；short 稳态、idle shared 均无劣化 |
| 7 | `-ncmoe` 必须跟着上下文一起调 | MoE 模型开启 `-ncmoe` 时，上下文越大需要的卸载层数越多；每层 ≈ 419 MiB，128K 用 22、256K 用 26 |
| 8 | 上下文余量是视觉预设的硬约束 | 128K 余量 657 MiB／256K 余量 495 MiB；跑前关闭占显存的程序（`llama-fit-params` 四项和不含 CUDA context + 桌面占用，约 +670 MiB，详见 §3 #17） |

> **通用教训**：
> - **视觉预设 = 文本预设 + `-mm` 投影器**，其余参数不动。投影器置于 CPU 是默认推荐方案（零显存成本 + 不占用 GPU 算力）。
> - **图像编码是一次性代价**，不是 decode 速度。对比视觉/文本 decode 速度时，应剔除首图编码点，只看同图 KV 前缀复用后的稳态值。
> - **`--image-min-tokens 1024` 是 Qwen-VL 系必加参数**，否则 grounding 任务会出错。
> - **`-ncmoe` 随上下文联动**：上下文增大时 KV buffer 膨胀，必须同步提高 `-ncmoe` 释放显存；否则溢出。
> - **视觉预设的上下文余量是硬约束**：128K 余量 657 MiB／256K 余量 495 MiB，跑前必须关闭占显存的程序。
