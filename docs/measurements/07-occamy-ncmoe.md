|---|---|---|---|---|---|---|---|---|---|
| 22 | 11354 | 233 | 64.9 / 79.1 / 78.4 | 74.1 | 74.0 | 744.1 | 31.4 | 87 | 15 |
| **20** | **11493** | **134** | 70.3 / 84.2 / 82.4 | **79.0** | **79.0** | **803.1** | **29.1** | 87 | 12 |
| 19 | 11672 | 256 | 70.9 / 82.8 / 86.7 | 80.1 | **7.5** | 816.1 | 43.9 | 96 | 59 |
| 18 | 11652 | 647 | 34.1 / 36.5 / 36.8 | 35.8 | 35.8 | 105.7 | 211.8 | 97 | 23 |
| 17 | 11745 | 1048 | 27.4 / 29.0 / 28.9 | 28.4 | 4.8 | 108.0 | 230.4 | 98 | 100 |
| 16 | 11686 | 1511 | 25.7 / 27.1 / 27.2 | 26.7 | 4.9 | 108.0 | 229.6 | 98 | 100 |

**结论：最优 `-ncmoe 20`** — idle shared 回落到 134 MB 基线，short/deep 均达最高值（79.0 t/s / 803.1 pps），prefill 803 pps。

## §4 上下文极限（idle shared 物理信号）

> `idle shared` 从 32K 基线（≈122–124 MB）跳升 = KV 溢出的物理信号。以下为 occamy 单模型在各 ctx / KV 类型下的实测值。

| KV | ctx | idle ded (MiB) | idle shared (MiB) | short ×3 (t/s) | 均值 |
|---|---|---|---|---|---|
| q8_0 | 32768 | 11265 | **122** | 69.5 / 80.4 / 86.0 | 78.6 |
| q8_0 | 65536 | 11637 | **154** | 69.5 / 84.0 / 87.0 | 80.2 |
| q8_0 | 98304 | 11712 | **540** | 70.8 / 80.9 / 86.0 | 79.2 |
| q4_0 | 32768 | 11105 | 124 | 69.7 / 82.3 / 84.7 | 78.9 |
| q4_0 | 98304 | 11585 | 188 | 69.1 / 82.2 / 86.6 | 79.3 |
| q4_0 | 131072 | 11733 | 348 | 69.7 / 82.3 / 86.1 | 79.4 |
| q4_0 | 163840 | 11758 | 632 | 70.3 / 81.8 / 77.4 | 76.5 |

**结论**：
- **q8_0 @96K 是溢出处**：idle shared 从 154 MB（64K）跳升到 540 MB（96K）→ KV 开始溢出共享内存。
- **q4_0 @160K**：idle shared 632 MB，仍在可控范围（未跳升），但短测均值已降到 76.5 t/s（长生成窗口下进一步下降）。
- 参考 §5 分段 prefill 结果：q8_0 在 96K 深填充下第 3 档（79K 深度）降至 72.5 pps → **q8_0 可用上下文约 80K**；q4_0 @160K 可用至 ~79K 深度。

## §5 分段 prefill 降级剖析（每档 ~26K tokens）

### 5.1 `-ncmoe 22` 将 q8_0 可用上下文提升至 128K

固定 `-t 16` / q8_0 / `-fa on` / `-ncmoe 22`，唯一变量 = ctx。以下为 `-ncmoe 22` 基准下的分段 prefill 与可容纳性验证结果。

#### 5.1.1 可容纳性验证（`scan_occamy_maxctx.ps1`）

固定 `-t 16` / q8_0 / `-fa on` / `-ncmoe 22`，唯一变量 = ctx：

| ctx | idle ded (MiB) | idle shared (MiB) | short ×3 (t/s) | 均值 | 判定 |
|---|---|---|---|---|---|
| 98304 | 11354 | 233 | 56.8 / 63.3 / 67.6 | 62.6 | 可容纳 |
| 114688 | 11573 | 249 | 56.1 / 67.7 / 73.6 | 65.8 | 可容纳 |
| **131072** | **11791** | **248** | 59.2 / 70.2 / 71.6 | 67.0 | ✅ **可容纳（上限）** |
| 147456 | 11842 | **392** | 59.1 / 67.8 / 71.6 | 66.2 | ⚠️ 起始溢出 |

**结论**：occamy `-ncmoe 22` + q8_0 最大可支持 131072（128K）；144K 开始出现溢出。

#### 5.1.2 可用深度验证（`prefill_profile.ps1 -Ncmoe 22 -Ctx 131072`）

128K 下的分段 prefill：

| 累计深度 | 17.6K | 35.2K | 52.8K | 70.4K | 88.0K | 105.6K | **123.3K** |
|---|---|---|---|---|---|---|---|
| pps | 611.2 | 623.0 | 623.3 | 605.9 | 589.6 | 575.3 | **564.2** |
| idle shared (MiB) | 248 | 248 | 248 | 248 | 248 | 248 | **248** |
| 该点 eval t/s | 58.4 | 61.3 | 53.5 | 52.9 | 51.0 | 48.1 | **45.5** |

**结论**：idle shared 全程保持恒定（248 MB），pps 全程仅下降 8%，至 123K 深度未见任何拐点。

**26.4K→123.3K 全深度可用，此为「可用」而非仅「可容纳」的直接证据。**

#### 5.1.3 显存账（上游 `llama-fit-params -fitp on`，CUDA0，MiB）

| ctx | model | KV (=context) | compute | 合计 |
|---|---|---|---|---|
| 98304 | 9075 | 1082 | 497 | 10654 |
| 131072 | 9075 | 1422 | 576 | 11073 |
| 262144 | 9075 | 2782 | 960 | 12817（> 12282 ✗ 不可容纳） |

- KV = 1422−1082 = 340 MiB / 32K = **10.6 MiB/1K tokens**（= 10880 B/token，与 GGUF 元数据推导一致）。
- **compute buffer 亦随 ctx 增长**（497→576→960，+2.4~2.9 MiB/1K）→ 上下文边际成本 ≈ **13.0~13.3 MiB/1K**（与 Windows 计数器实测的 96K→128K 段 +13.3 MiB/1K 一致，理论推导与实测相符）。
- 总预算 12282 = 系统/桌面保留 + CUDA context + model 9075 + KV + compute；由实测溢出点（144K）反解「保留+其他」≈ 950 MB → 估计极限 ≈147K（估计偏乐观），**实测：128K 正常 / 144K 起始溢出** → 取 **131072** 为安全上限。

#### 5.1.4 代价（同会话，t=14，1500 tokens 稳态）

`-ncmoe 22` 稳态 decode `67.6/69.7 → 68.65` t/s。

> **结论（取代 §5.1）**：occamy q8_0 可用上下文以 **`-ncmoe 22`** 为基准，为 **128K（131072）**。**128K+q8_0 在精度与深度上均全面优于原 q4_0@160K**（后者仅可用至 ~79K 深度），代价为 decode 下降 6%。

## §7 视觉预设（mmproj 置于 CPU）

> 本章为视觉预设专项实测记录（2026-10，全部 L2）；occamy 总体结论以本文 §0~§7 为准。

### 7.1 结论速览

| 问题 | 答案 |
|---|---|
| 投影器能否加载 | ✅ `loaded multimodal model`，视觉通路实测可用 |
| **投影器置于 CPU 占多少显存** | **0 MiB** — 专用显存与"不加载投影器"逐位相同（10585 MiB） |
| **投影器置于 GPU 占多少显存** | **+1110 MiB**（10585 → 11695 MiB） |
| **文本预设的参数值能不能直接用于视觉预设** | ✅ **能，全部成立**（详见 `00-测试项目共同经验.md §7 #6`） |
| **上下文上限** | ✅ **131072（128K）真实可用**：123K 深填充全程零溢出，prefill 仅下降 13.6% |
| **256K 极限档可行性** | ✅ **262144（256K）+ `-ncmoe 26` 可用**（余量仅 495 MiB）：210K 深填充零溢出、图像回答正确、图像编码**不占用 CUDA0 显存** |
| 是否必须 `-ncmoe 24`（35B 旧结论） | ❌ **不适用**。原结论因投影器占用显存所致；投影器置于 CPU 后 `-ncmoe 22` 即可满足，且 22 较 24 速率更优 |
| **视觉预设完整命令** | 见 **§2.5** |

### 7.2 投影器位置：显存成本 A/B（唯一变量 = 投影器位置，ctx 32768）

| 用例 | 投影器 | 专用显存 | Δ vs 基线 | idle shared | short ×3 均值 |
|---|---|---|---|---|---|
| A 纯文本（不加载） | — | 10585 MiB | +10037 | 142 | 64.5 t/s |
| **B 投影器置于 CPU** | `-mmdev none` | **10585 MiB** | **+10037（= 0 额外）** | 142 | 65.2 t/s |
| C 投影器置于 GPU | `--mmproj-offload` | 11695 MiB | +11147（**+1110**） | 142 | 65.2 t/s |

**`-lv 4` 的 buffer 账（判定投影器落在哪个设备）**：

| 用例 | CPU compute | CUDA0 compute | 说明 |
|---|---|---|---|
| A 纯文本 | 40.3 MiB | 360.0 MiB | 基线 |
| B 置于 CPU | **248.1 MiB** | 360.0 MiB | 投影器（≈208 MiB 增量）落在 **CPU**，CUDA0 未变 |
| C 置于 GPU | 24.9 MiB | **248.1 MiB** | 同一块 buffer 搬至 CUDA0 → 占用显存 |

**上游取证**：`common/arg.cpp` 中 `-mmdev none` 执行 `mmproj_use_gpu=false; mmproj_device=nullptr` 后立即 `return`，与 `--no-mmproj-offload` 等价且**顺序安全**（`-mmdev` 在 `--mmproj-offload` 之后解析不会被覆盖）。

### 7.3 文本预设参数在视觉预设下的适用性

实测（ctx 32768）：KV q8_0 buffer 340 MiB、compute 360 MiB、模型 9075.7 MiB —— **与纯文本逐项一致**；short 稳态 65.2 t/s（纯文本 64.5）→ 无劣化；idle shared 维持在 142 MiB → 无溢出。

| 累计深度 | prefill pps |
|---|---|
| 17,488 | 515.6 |
| 69,966 | 510.4 |
| 122,454 | 473.4 |
| 174,942 | 437.0 |
| **209,934** | **431.7** |

> ⚠️ **两项关键约束**：
> 1. **余量仅 495 MiB**，低于题①估算值（639 MiB）。实测比 `llama-fit-params` 四项和多 670.5 MiB（见 `00-测试项目共同经验.md §3 #17`）。
> 2. **运行前需关闭占用显存的应用程序。** 空载基线 533 MiB；桌面多占用 200–300 MiB 时此档位即开始溢出。如需更宽裕余量，可降级至 `-ncmoe 27`（按实测 419 MiB/层 ≈ 余量 914 MiB，代价 decode 再下降 2–3%）。

#### 7.4.4 文本与视觉 decode 速度对比（同会话交替实测，256K / ncmoe 26）

> **澄清**：图像编码 ≠ 文本 prefill（见 `00-测试项目共同经验.md §7`）。实际应对比 **decode t/s** —— 投影器不参与逐 token 生成。

填充到 209,934 tokens 后，在同一会话内交替测量（每档 3 次，`max_tokens=120`）：

| 档位 | decode t/s（有效值） | 均值 | 图像编码 prompt_ms |
|---|---|---|---|
| 文本（第 1 轮） | 34.5 / 35.1 / 35.1 | **34.9** | — |
| **视觉**（带图） | **34.9**（34.8 / 35.0 稳态均值） | **34.9** | **14665**（首次，1048 tokens）／120／111 |
| 文本（复测，排除时间漂移） | 35.0 / 35.3 / 35.3 | **35.2** | — |

- **稳态 decode 速度相同**：视觉 34.8 / 35.0 vs 文本 35.0–35.3 → **比值 ≈ 1.00**（差 0.3%，在噪声内）。
- **视觉第 1 次偏低（31.8）为一次性代价**：首图 1048 tokens 编码 **14.7s**，使该次平均值偏低；此点为**一次性图像编码成本**，非 decode 速度，已剔除出有效 decode 读数。第 2、3 次同图经 KV 前缀复用，编码降至 **111–120ms**，decode 恢复至文本水平。
- 时间漂移检查：文本复测/首测 = **100.9%** → 上表差异不是漂移造成的。

#### 7.4.5 256K 与 128K decode 速度差异分析

| 档位 | decode t/s |
|---|---|
| 128K / ncmoe 26（同批实测） | 56.4 |
| **256K / ncmoe 26（本节）** | **34.9** |

降幅 **−38%**，指向 KV 规模（1360 → 2720 MiB）带来的注意力成本，**而非**投影器所致（同档纯文本亦为 34.9 t/s）。此现象与 §3 所述「`-ncmoe` 为 decode 速度与可用上下文的调控旋钮」机制一致，此处变量为上下文而非卸载档位。

### 7.5 部署建议（视觉预设）

> 视觉预设完整启动命令见 **§2.5**。以下为两档部署总结（均含投影器置于 CPU）：

| 档位 | 关键参数 | 显存余量 | decode | prefill | 适用 |
|---|---|---|---|---|---|
| **① 128K（推荐默认）** | `-c 131072 -ncmoe 22 -rb 65536` | 657 MiB | 46.5→69.2 t/s（随深度） | 682→589 pps | 日常；余量宽、速率优 |
| **② 256K（极限）** | `-c 262144 -ncmoe 26 -rb 131072` | **495 MiB** | **34.9 t/s** | 515→432 pps | 需要超长上下文；边界运行，须关闭后台应用 |

- **`-ncmoe` 须随上下文联动调整**（见 `00-测试项目共同经验.md §7 #7`）。
- **上下文余量为两档的硬约束**（见 `00-测试项目共同经验.md §7 #8`）。
- 视觉预设的通用部署经验已统一记录于 `00-测试项目共同经验.md §7`。
