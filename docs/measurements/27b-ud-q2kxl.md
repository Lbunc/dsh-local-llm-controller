# Qwen3.8-27B-UD-Q2\_K\_XL（9.15GB，dense，比 IQ3\_XXS 更小）

> 拆分自《本地模型调优全历程终版存档》，编号保留原章节号（§N.x）以便交叉引用；测量方法论见 [../llm-experiment-design/SKILL.md](../llm-experiment-design/SKILL.md)。

> 与第 5 章 IQ3\_XXS（10.18GB）同为 `qwen35` dense 架构（65 层 / 16 KV 层 / 原生 ctx 262144 / KV/token f16=65536B），**仅量化更激进（Q2\_K\_XL 9.15GB 省 \~1GB）**。测于 2026-08 干净环境。

### 6.8.1 核心结论（★比 IQ3\_XXS 能撑更高上下文）

**省下的 ~1GB 显存全给了 KV → q4\_0 上下文上限从 IQ3\_XXS 的 48K 提升到 96K**，且速度更快（37 vs 33 t/s）。

| KV 档 | 32K   | 48K   | 64K   | 80K   | 96K   | 112K  |
| ------ | ----- | ----- | ----- | ----- | ----- | ----- |
| **q8\_0** | 36.7  | 37.5  | 27.1 ⚠️ | 10.2  | 14.1  | 13.6  |
| **q4\_0** | 36.5  | 37.1  | 36.6  | 36.6  | 37.3  | 15.0 ⚠️ |

（数值 = short 稳态 t/s；⚠️ = shared 跳升 >300MB 溢出信号。q8\_0 断崖 64K；q4\_0 断崖 112K。）

### 6.8.2 断崖判定（shared 物理信号）

- **q8\_0**：48K=37.5（shared 169）→ 64K=27.1（shared **337**）→ 80K shared 937 → **断崖在 64K**。
- **q4\_0**：32K\~96K shared 146→210（平缓，无溢出）→ 112K shared **382 / 378** → **断崖在 112K**，**最优 96K**。

### 6.8.3 ★可用上下文（prefill/墙钟，跟 IQ3\_XXS 无关的关键差异）

与 35B MoE"极限上下文 prefill 慢到不可用"不同，本 dense 27B **prefill 极快（pps ≈950-1120）**，故 96K 真实可用：

| ctx  | 填充深度 | prefill pps | prompt\_ms | eval t/s | **总墙钟** | GPU | 可用性 |
| ---- | ------ | --------- | ---------- | ------- | -------- | ----- | ----- |
| 64K  | 57214t | 1004.9    | 56938      | 27.0    | 71.7s    | 97%  | ✅    |
| 96K  | 73942t | 952.9      | 77601      | 25.0    | **85.6s** | 97%  | ✅（重测 947.8/85.9s，可重复） |
| 112K | 86989t | 663.1      | 131179     | 16.8    | **143s**  | 99%  | ❌ prefill 掉档，不可用 |

→ **最大可用上下文 = 96K（98304）**：生成 25-37 t/s + prefill \~950 p/s、一次请求 \~86s。112K 时 prefill 掉档、wall 143s，交互/agent 不可用。**"能装下"（KV 断言）与"能用"（prefill/墙钟）在此断崖一致**——112K 是双重不可用。

### 6.8.4 推荐配置

```
llama-server.exe -m .\qwen3.8-27B\Qwen3.8-27B-UD-Q2_K_XL.gguf -a qwen38-27b-xl
  --port 55555 --host 127.0.0.1
  -ngl 99 -c 98304 -fa on --cache-type-k q4_0 --cache-type-v q4_0
  -t 20 -tb 20 -np 1 --reasoning-budget 2048
  --temp 0.6 --top-k 20 --top-p 0.95 --min-p 0.0
  --repeat-penalty 1 --presence-penalty 0 --metrics --slots
```

- **最佳上下文 = 96K（98304）**：q4\_0 下 32K\~96K 速度持平（36.5\~37.3 t/s），取满即 96K 无速度代价。
- **速度优先**：`-c 32768` = 36.5 t/s；**长上下文用 q4\_0 @96K**（30K+ 仍 37.3，3× 上下文）。
- **不与 IQ3\_XXS 冲突**：IQ3\_XXS 上下文 32K（48K 断崖）→ 本模型更大上下文 + 更快，但能力同档。**选型依据 = 需要多长上下文**：≤32K 两者均可；>32K 用 Q2\_K\_XL（能到 96K）。

### 6.8.5 能力对比：Q2\_K\_XL（2-bit）vs IQ3\_XXS（3-bit）@32K

公平规则：同构（dense 27B）/ 同参（-ngl 99 + KV q4\_0 + 32K + rb2048）/ 同题 / objective 判定。精确计算题各 3 次 + 编程题 test cases 判分。**唯一变量 = 量化档（2-bit vs 3-bit）**。

| 题                    | Q2\_K\_XL | IQ3\_XXS |
| --------------------- | --------- | -------- |
| 精确链式（x5=615）        | 100%      | 100%     |
| 二次优化（P=80, 利润 44000） | 100%      | 100%     |
| 多步计算（产线=1131）        | 100%      | 100%     |
| 数论（剩余定理=157）         | 100%      | 100%     |
| 编程 LRU 缓存            | PASS      | PASS     |
| 编程 有效括号             | PASS      | PASS     |
| **平均**               | **100%**  | **100%** |

→ **能力完全同档**。2-bit 量化对这组题无损（都是 27B 同架构，仅 bit 数不同；+数学精确题仍全对）。**注意**：题库偏基础，对梯度较小的量化档**无区分度**；如需验证"2-bit 是否伤能力"，需更高难度题（多跳精确计算/进阶算法），但这不是 32K 上下文场景的重点——选型核心仍是**上下文上限（Q2\_K\_XL 96K > IQ3\_XXS 48K）**。

### 6.8.6 ★投机解码（MTP）——大收益（与 IQ3\_XXS 相反！）

**判定门**：模型带 nextn MTP 头（`blk.64.nextn.*`）+ GPU 未饱和（base long 94%→89%）。**关键差异**：Q2\_K\_XL 比 IQ3\_XXS 更小更轻 → GPU 有空闲给 draft 摊薄，**MTP 大幅提速**（IQ3\_XXS 当时 GPU 86-98% 耗尽，MTP 反而更慢）。

| 模式 | short t/s | long t/s | 接受率 | GPU tail | idle ded | 额外显存 |
| ---- | -------- | -------- | ----- | -------- | ------- | ------- |
| base(无) | 36.5/37.1 | 36.5    | —     | 94%      | 10277   | —       |
| **MTP n=2** | **57.3/57.2** | **51.7** | **63.1%** | 89% | 11173 | +896MB |
| MTP n=3 | 58/55   | 48.2    | 50.1% | 88%      | 11326   | +1049MB |
| MTP n=4 | 57.2/54.6 | 49.8   | 43.3% | 79%      | 11479   | +1202MB |

**复核（重复 ≥2）**：base 36.3 → MTP n=2 **48.1 t/s**（long，+32%），接受率 60.7%，short 56-59。**提升稳定（+32~42%）。**

- **最优 `--spec-type draft-mtp --spec-draft-n-max 2`**：long 51.7 t/s（比 base **+42%**）、接受率 63.1%（>0.65≈优秀）、short +57%。
- **接受率随 n 衰减**（n=2 63% → n=3 50% → n=4 43%）→ **n=2 是甜点**（续 9B 结论：n 越大 draft 越长、验证批量分摊收益递减，n=2 最优）。
- **代价**：额外 +896MB 显存（MTP 缓冲 + 上下文预算），32K 无逸出。

### 6.8.7 推荐配置（含 MTP）——注意 32K vs 64K 权衡

---
**① 文本速度最优（32K）**：
```
llama-server.exe -m .\qwen3.8-27B\Qwen3.8-27B-UD-Q2_K_XL.gguf -a qwen38-27b-xl
  --port 55555 --host 127.0.0.1
  -ngl 99 -c 32768 -fa on --cache-type-k q4_0 --cache-type-v q4_0
  -t 20 -tb 20 -np 1 --reasoning-budget 2048
  --spec-type draft-mtp --spec-draft-n-max 2
  --temp 0.6 --top-k 20 --top-p 0.95 --min-p 0.0
  --repeat-penalty 1 --presence-penalty 0 --metrics --slots
```

**② 长上下文（64K，MTP 上限）**：同上但 `-c 65536`。

- **文本速度优先**：MTP n=2 @32K → 51-57 t/s（比无 MTP 36.5 快 **+32~42%**）。
- **MTP + 上下文权衡**：MTP 额外 +896MB → 上下文上限**从无 MTP 的 96K 降到 64K**（见 6.8.8）。**不能同时要"最快+最高上下文"。**

### 6.8.8 ★MTP n=2 下的上下文上限（= 64K）

MTP +896MB 挤占 KV 余量 → **最大可用上下文 = 64K**（无 MTP 是 96K）。

**短测 shared**（冷启动分配，显 MTP 缓冲+KV 预分配）：

| ctx | short t/s | shared | 判定 |
| ---- | -------- | ------ | ---- |
| 32K | 60.2 | 280 | ✅ |
| 48K | 57.6 | 311 | 临界 |
| **64K** | 59.8 | 439 | ⚠️ 短测信号 |
| 80K | 41.9 | 919 | ⚠️ |
| 96K | 18.0 | 1400 | ⚠️ |
| 112K | 42.5 | 1548 | ⚠️ |

**深填充/墙钟可用性**（真实判据，MTP 增益是否保留 + prefill 是否可接受）：

| ctx | 填充深度 | prefill pps | eval t/s | wall | shared | 接受率 | 可用 |
| ---- | ------ | --------- | -------- | ---- | ------ | ------ | ---- |
| 48K | 30454t | 1079.3 | 48.0 | 32.4s | 277 | 75.8% | ✅ |
| **64K** | 47848t | 998.8 | **41.8** | 52.7s | 310 | 73.8% | ✅（复核 870/41.2/59.8s/71.8%，可重复） |
| 80K | 60895t | 390 | 7.5 | **182.6s** | 786 | 0% | ❌ prefill 掉档+MTP 失效 |
| 96K | — | — | — | 超时>8min | 1134 | — | ❌ 深填充跑不完 |

→ **MTP n=2 最大可用上下文 = 64K**：MTP 增益保持（eval 41.8 vs 无 MTP 的 ~36）、prefill 仍快（~1000 p/s）、wall 52.7s 可用。**80K 即硬断崖**——prefill 掉到 390、MTP 接受率归零、wall 182.6s 不可用；96K 深填充直接跑不完。**注意**：短测 64K shared 显示"溢出信号"（439），但深填充运行时 shared 仅 310——**短测为冷启动分配，不影响真实可用性**；"能装下"用深填充 shared + wall 判定。
