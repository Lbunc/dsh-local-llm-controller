→ **occamy 胜在 decode（长回答、agent 多轮续写），UD 胜在 prefill（长文档一次性读入）。**

## E. ★decode 相四件套修正 + CPU 线程扫描（-t）

### E.0 首轮四件套的采样窗口污染（用户发现 CPU 占用偏低后定位）

首轮扫描脚本把 util 采样器套在"深填充"调用上，而该调用墙钟被 prefill 主导：
`ncmoe=20` 深填充 `prompt_ms=27398` vs `predicted_n=128`（≈1.6s @79t/s）→ **decode 只占窗口 5%**，
测到的 `gpu=87% / cpu=12%` 实际是 **prefill 画像**（prefill 是矩阵×矩阵，GPU 重、CPU 几乎不动）。
修正方法：**极短 prompt（27 tokens）+ 长生成（1500 tokens）**，让窗口由 decode 主导。
另：脚本里 `sm_clk/power` 是在请求返回后才采的（GPU 已回落空闲）→ **该两列无效，勿引用**。

### E.1 decode 相真实画像（occamy，ncmoe 20 / q8_0 / -t 20，1500 tokens 持续生成）

| 指标 | 实测 | 判读 |
|---|---|---|
| GPU util（生成期尾部均值） | **47-54%** | GPU 约一半时间空闲 |
| GPU 功耗（能力题库长生成期实测） | **102.8 W / 220 W** | 远离功耗墙 |
| GPU SM 时钟（生成期） | 2910 / 3150 MHz | 未降频 |
| CPU 总占用 | **100%**，20/20 逻辑核 | CPU 饱和 |
| llama-server cores_busy | **17.69 / 20** | 进程级确认 |
| 内核态占比（长生成期一次采样） | ≈ 3.6 核 | mmap 缺页/WDDM 开销 |

→ **decode 阶段是 CPU-bound，GPU 有近一半算力与近一半功耗余量闲置。**
（`user/priv` 单次瞬时采样噪声大，仅作参考；`cores_busy` 用进程 CPU 差/墙钟，可信。）

### E.2 ★CPU 线程扫描（-t，ncmoe 20 / q8_0 / 32K / 1500 tokens）—— 判定门：有 CPU 专家卸载 → 必扫

occamy（-ncmoe 20）：

|---|---|---|---|---|
| 20 | 68.1 | 47 | 100 | 17.69 |

→ **-t 16 比 -t 20 快 17.3%**（79.9 vs 68.1）。CPU 在 t=20 已 100% 饱和却更慢，
是典型的 **i5-13600KF 混合核（6P+8E）线程超配**：20 线程会被排到 E-core 与 P-core 超线程上，
自旋/同步开销吃掉收益。**默认 `-t 20` 不是最优。**

同批 ncmoe 对照（-t 20）：22 → 62.0、20 → 68.1、19 → 66.3、19+q4_0 → 66.6
→ 与首轮 short 测的排序（19 > 20 > 22）一致，但绝对值整体更低（长生成比 160-token 短生成更苛刻）。

|---|---|---|---|

→ UD 最优也在 ~12-20 之间但幅度小（+3%）；occamy 的 t=16 增益（+17%）需复测确认（见 F）。

**注**：本表 occamy@t20 = 68.1 t/s 低于首轮 `Invoke-Short`（160 tokens）的 78-80 t/s。
差异来源 = 生成长度（160 vs 1500 tokens）：短生成有 CUDA graph/缓存热度红利，长生成是稳态。
→ **对外报速度必须注明生成长度**，否则跨表不可比。

### F.4 c3 编程题：首轮判分是**假阴性**（harness 缺陷，非能力差）

- 首轮 occamy 0%/0%、UD 100%/0%。排查发现**两处 harness 缺陷**：
  1. **多代码块被拼接**：模型常给多份实现（occamy 一次 11 个 ``` fence、另一次 47 个）→
     旧 `Get-PythonCode` 把它们拼成一个文件，同名函数/类互相覆盖 + 混入截断残块 → exec 失败。
  2. **token 预算不足**：c3 用 6144/8192 生成三大段代码会被截断（无闭合 fence）。
- 修正：拆块后**每块单独跑测试取最高分**，`maxtok` 提到 10240，复测 3 次。结果见报告 F.4。

  正是 Windows 计数器实测的 96K→128K 段 +13.3 MiB/1K —— **账对上了**。
- 总预算 12282 = 系统/桌面保留 + CUDA context + model 9075 + KV + compute；
  由实测溢出点（144K）反解「保留+其他」≈ 950 MB → 估计极限 ≈147K（估计偏乐观），
  **实测：128K 干净 / 144K 起溢出** → 取 **131072** 为安全上限。

### G.3 `-t` 的理论值：取证 + 单进程曲线

**取证（谁是「自动」）**：
- `llama-server` 不传 `-t` → 日志 `init: llama threadpool init, n_threads = 14`
- `llama-bench -h` → `-t, --threads <n> (default: 14)`
- `Win32_Processor`: **NumberOfCores = 14 / NumberOfLogicalProcessors = 20**（6P+8E，P 核有 HT）
→ llama.cpp 自己的 auto = **物理核数 14**，不是逻辑核数 20。

### G.4 `-ncmoe 22` 的代价（同会话，t=14，1500 tokens）

| 指标 | ncmoe 20 | ncmoe 22 | 差 |
|---|---|---|---|
| decode t/s（2 次） | 73.9 / 72.5 → **73.2** | 67.6 / 69.7 → **68.65** | **−6.2%** |
| idle shared @32K | 152 / 189 | 152 / 190 | 同为基线（都无溢出） |
| 能撑的 q8_0 ctx | ~80K | **128K** | **+60%** |
| prefill（17.6K 档 / 128K ctx） | — | 611.2 pps | 比 ncmoe 20@80K 首档 668 低 ~9% |

→ **一句话**：`-ncmoe` 是「decode 速度 ↔ 可用上下文」的旋钮。22 比 20 慢 6%，换来 q8_0 可用上下文从 80K 到 128K；
且 128K+q8_0 在**精度和深度上都优于**原来的 q4_0@160K（后者只能用到 ~79K 深度）。
