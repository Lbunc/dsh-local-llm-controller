### 2.3 部署经验与约束

- **b10883 勘误（见 §5.2）**：旧版（b10488）"48K 断崖"修正为 **断崖带 64K↔80K**（b10883 干净环境 64K@N=0 无损，33.3 t/s、shared 242 MB）。本节所有后续配置以 b10883 复核为准。
- **`-ncffn N` 救援原则**：按"溢出多少补多少"选最小 N（每层 FFN 卸载释放 ≈75MB 显存）。N=16 救 80K（+79% 速度、shared 归零）；N=24 救 96K–128K（+27% 速度、shared 归零）。
- **`-ncffn` 与 MTP 不叠加**：12GB 卡上二者只选一个。IQ3_XXS 救援场景选纯 `-ncffn`（MTP draft 缓冲 +0.6–1.1GB 会吃回 -ncffn 腾出的余量）。
- **`-t/-tb` 线程**：默认 `n_threads = 物理核数 14`（见 `00-测试项目共同经验.md §5`）。
- **思考模式必设 `--reasoning-budget`**：默认 xhigh 会烧掉 9000+ token 预算，吃光 `max_tokens` 导致空 content。

## §3 KV 量化对照与上下文断崖（-ngl 99 全 GPU）

> 判定门：dense 65 层全 GPU 后权重占满显存（ded≈11.7GB），只剩 ~0.3GB 给 KV → 32K 已临界。
> b10883 复核修正断崖地图：**断崖带从 48K 移至 64K↔80K**。

### 3.1 上下文断崖（-ngl 99 / q8_0 vs q4_0）

| C | q8_0 shared (MiB) | q8_0 t/s | q4_0 shared (MiB) | q4_0 t/s |
|---|---|---|---|---|
| **32K** | 277 | **24.5** | 161 | **33.7** |
| **48K** | 741 | **10.4** | 242 | 26.3 |
| 64K | — | — | 305 | 22.2 |
| 80K | — | — | 700 | 14.6 ❌ |
| 96K | — | — | 831 | 10.4 ❌ |

**结论（b10883 复核）**：
- **q8_0 @32K → 48K 是断崖**（t/s 从 24.5 腰斩至 10.4，shared 从 277 MB 暴涨至 741 MB）。
- **q4_0 @32K–64K 无损**：32K=33.7 t/s（shared 161 MB）、64K=22.2 t/s（shared 305 MB，仍在可控范围）。
- **断崖带在 64K↔80K**（80K shared 700 MB ⚠️、t/s 降至 14.6；96K shared 831 MB ⚠️、t/s 降至 10.4）。
- **实际最佳上下文 = 64K**（q4_0，b10883 复核无损可用）。

### 3.2 KV 量化对照（32K / -ngl 99）

| KV | shared (MiB) | t/s | 推理题 |
|---|---|---|---|
| **q4_0** | 164 | **33.0** | ✅ |
| q8_0 | 309 | 31.6 | ✅ |
| f16 | 1215 | **12.7** | ❌ → 32K 断崖，禁用 |

**结论**：q4_0 在 32K 下速度最快（33.0 t/s）、显存占用最低（164 MB），且推理题全部通过。f16 KV 直接导致 32K 断崖（shared 1215 MB，t/s 仅 12.7）。**推荐 q4_0 KV**。

### 3.3 显存账（上游 `llama-fit-params -fitp on`，CUDA0，MiB）

| ctx | model | KV (=context) | compute | 合计 |
|---|---|---|---|---|
| 65536 | ~7348 | ~242 | ~360 | ~7950（< 12282 ✅） |
| 98304 | ~7348 | ~363 | ~576 | ~8287（< 12282 ✅，余量收窄） |

**结论**：dense 65 层权重占满显存（ded≈11.7GB → model≈7348 MiB + CUDA context + 桌面占用 ≈950 MB），q4_0 KV @64K（305 MiB）仍可容纳，@96K（363 MiB）余量收窄至 ~200MB。

## §4 -ngl 真卸载测试（32K / q8_0，不划算）

> 稠密每 token 读所有层，卸载层走 CPU 代价极高（省 0.6GB t/s 腰斩）。早前 `-ngl 90/95` 均 ≥65 层=假卸载（全层仍上 GPU）无差异。

### 4.1 -ngl 网格扫描（32K / q8_0）

| -ngl | GPU 层 | idle ded (MiB) | t/s |
|---|---|---|---|
| 99 | 65/65 | 11774 | **29.3** |
| 60 | 60/65 | 11148 | 16.9 |
| 50 | 50/65 | 9877 | 10.2 |

**结论**：稠密模型每 token 读所有层，卸载层走 CPU 代价极高（省 0.6GB → t/s 从 29.3 腰斩至 16.9 / 10.2）。**-ngl 真卸载不划算**，推荐使用 `-ngl 99` 全 GPU。

### 4.2 假卸载说明（-ngl 90/95）

| -ngl | GPU 层 | 判定 |
|---|---|---|
| 90 | 65/65（全部） | 假卸载（全层仍上 GPU，与 -ngl 99 无差异） |
| 95 | 65/65（全部） | 假卸载（同上） |
| 99 | 65/65（全部） | 真全 GPU |

**结论**：65 层模型 -ngl ≥65 时全部层仍在 GPU，-ngl 90/95 为假卸载（无实际卸载效果）。仅 `-ngl <65` 才触发真卸载（代价极高，见 §4.1）。

## §5 -ncffn 新参数实测（b10883，溢出救援）

> **参数语义**（[PR #26622](https://github.com/ggml-org/llama.cpp/pull/26622)，b10883 可用）：`-ncffn N` 把**前 N 层的 dense FFN 权重**（`blk.0..N-1.ffn_up/down/gate`）留在 CPU 内存（tensor 级 buft override），attention/SSM/norm 仍按 `-ngl 99` 在 GPU。即 `--n-cpu-moe`（MoE 专家版）的 **dense 对应物**。
>
> **张量名命中验证**：qwen35 的 195/195 FFN 张量全部命中 regex（`gguf_ffn_probe.ps1`，两个量化档皆命中）→ 机制在此模型真实生效。

### 5.1 32K 纯吞吐：-ncffn 不是提速参数（dense 上纯负）

| -ncffn N | idle ded (MiB) | 腾出显存 | short t/s | GPU% | CPU% |
|---|---|---|---|---|---|
| 0 | 11479 | — | **33.9 / 33.3**（多会话一致） | 90→87 | 12→10 |
| 8 | 10875 | −604MB | 23.5 / 23.5 | 59 | **89** |
| 16 | 10360 | −1119MB | 18.0 / 18.1 | 50 | **100** |
| 24 | 9702 | −1777MB | 14.2 / 14.2 | 42 | 100 |
| 32 | 8913 | −2566MB | 11.4 / 11.3 | 31 | 100 |
| 48 | 7317 | −4162MB | 7.4 / 7.3 | 33 | 100 |

**结论**：每层 FFN 卸载释放 **≈75MB** 显存，但 **N=8 就已把瓶颈从 GPU 推到 CPU**（dense FFN 每 token 必经、矩阵×向量纯权重带宽 bound，20 线程 89% 饱和），t/s 单调腰斩：33→23.5→18→14→11→7。**`-ncffn` 在 32K 纯吞吐上是纯负参数**（与 MoE `-ncmoe` 本质区别：MoE 专家仅激活时才算、dense FFN 全量每 token 必算）。

### 5.2 -ncffn 参数实测：大上下文溢出救援与断崖地图修正（b10883 复核）

同会话先重扫基线：**b10883 干净环境下 64K@N=0 已无恙（33.3 t/s、shared 242）**→ 旧版（b10488）"48K 断崖"修正为 **断崖带 64K↔80K**。在此新地图上：

| ctx | N=0（基线） | 救援配置 | 救援后 | Δ |
|---|---|---|---|---|
| 64K | **33.3**，shared 242 无溢出 | （不需要） | — | 用 -ncffn 反而自伤（N=16→17.7） |
| 80K | **10.4 ⚠️** shared 897 | **`-ncffn 16`** | **18.6**，shared 193 | **+79%** 且溢出清零 |
| 96K | **11.1 ⚠️** shared 1092 | **`-ncffn 24`** | **14.1**，shared 210 | **+27%** 且溢出清零 |
| 128K | 14.5 ⚠️ **shared 2026**（2GB 溢出） | `-ncffn 24` | 15.8，shared 234 | 速度持平、**2GB 溢出清零**（去 WDDM 分页风险） |

**深填充可用性**（判"可用"，非只"可容纳"）：
- **80K@N=16**：填 60.9K tokens，WALL 78.4s（prefill **911.8 pps**、eval 17.2）✅
- **96K@N=24**：填 73.9K tokens，WALL 108.7s（prefill 786.3、eval 13.6）✅

**关键机制**：ncffn 的 CPU 瓶颈**只在 decode**（矩阵×向量、权重带宽 bound）；**prefill 是矩阵×矩阵，权重读取被 batch 摊薄，几乎不掉速**（912/786 pps ≈ 全 GPU 基线的 950–1120）。"可容纳"与"可用"在救援点同时成立。

### 5.3 ×MTP 交互：plateau 有回升，但不叠加（12GB 卡）

| 配置（MTP n=2） | plateau short | vs 无 MTP | 接受率 | shared (MiB) |
|---|---|---|---|---|
| 80K N=16 | 21.9 / 22.2 | +18% | 63.8% | **804 ⚠️ 回溢出区** |
| 96K N=24 | 15.5 / 14.7 | +7% | 63.2% | 576 ⚠️ |
| 128K N=24 | 15.8 / 15.0 | ≈0 | 62.0% | 1536 ⚠️ |
| 32K N=24 | 14.6 / 15.1 | ≈0 | 60.2% | 192 ✅ |

**结论**：MTP 批量验证确实摊薄了 CPU FFN 的单 token 权重成本（接受率 60–64% 健康、80K 点 +18%），但 **MTP 自身 draft 缓冲 +0.6–1.1GB 把 ncffn 刚腾出的余量吃回**，shared 重新跳升 → 两个省/花显存的机制互相抵消，救援目标（零溢出）被破坏。**12GB 卡上二者只选一个；IQ3_XXS 救援场景选纯 -ncffn**。

## §6 MTP / reasoning_effort 测试

### 6.1 MTP 测试（-ngl 99 / q4_0 / 32K）

| 模式 | GPU tail | idle ded (MiB) | 判定 |
|---|---|---|---|
| base（无 MTP） | 86%→98% | 10277 | GPU 已饱和 |
| draft-mtp | — | 1271 | shared 顶到 1271MB，更慢（29.5→17.6） |

**结论**：**MTP 不推荐**（dense 27B IQ3_XXS：GPU 已 86%→98% 饱和，draft-mtp 反而更慢（29.5→17.6），shared 顶到 1271MB）。与 9B / 27B XL 相反（后两者 GPU 未饱和，MTP 大幅提速）。

### 6.2 reasoning_effort 测试

| 档位 | wire 值 | 思考字符数 | 答案正确性 |
|---|---|---|---|
| off | `off` | — | 关思考 |
| low | `low` | — | 注入 low 指令 |
| medium | `medium` | 563 | 仍正确（需 server 启动参数，本 build 不接受请求级字段） |
| xhigh（默认） | `xhigh` | 1692 | 默认行为 |

**别名**：`high`/`max`/`ultracode`/`extreme`→`xhigh`；`minimal`→`low`；`off`/`none`→关思考。
**结论**：`medium` 档位（563 字符）可减少思考长度同时保持答案正确，适合对延迟敏感的场景。**必设 `--reasoning-budget 2048`**（默认 xhigh 会烧掉 9000+ token 预算）。

## §7 能力评测与选型建议

### 7.1 能力验证（32K 最终配置）

| 测试项 | 结果 |
|---|---|
| 多步规划 | 100% ✅ |
| 工具调用编排 | 100% ✅ |
| LRU 缓存 | PASS ✅ |
| 有效括号 | PASS ✅ |

**结论**：能力优秀，27B dense 在基础推理与编程题上表现稳定。

### 7.2 贪心对照（temp=0）跨后端非位一致

* **贪心对照**（temp=0）：N=24 从第 8 字符即与 N=0 分叉，一道 4 步算术链一次答错（2808 vs 正确 2534）。同配置自复现 100% 一致 → 分叉源于 **CUDA vs ggml-CPU 浮点累加顺序不同**（权重未变，≠量化降精度），贪心 argmax 把末位噪声级联放大。
* **客观判分**（temp 0.6 × 3 题 × 3 次，reference 程序生成标准答案）：**N=0 = N=16 = N=24 = 9/9（100%）** → **真实采样下能力无损**。
* **实操含义**：依赖 temp=0 跨配置严格复现输出的场景（回归测试/快照比对）不要混用 ncffn 开关；常规使用不受影响。

### 7.3 -ncffn 救援总结

| 上下文 | N=0 基线 | 救援配置 | 救援后 | 墙钟 | 可用性 |
|---|---|---|---|---|---|
| 64K | 33.3 t/s, shared 242 | （不需要） | — | — | ✅ 默认首选 |
| 80K | 10.4 ⚠️, shared 897 | -ncffn 16 | 18.6, shared 193 | 78.4s | ✅ 可用 |
| 96K | 11.1 ⚠️, shared 1092 | -ncffn 24 | 14.1, shared 210 | 108.7s | ✅ 可用 |
| 128K | 14.5 ⚠️, shared 2026 | -ncffn 24 | 15.8, shared 234 | >150s（估算） | ⚠️ 仅非交互批量 |

**一句话回答"这个参数对 27B 有什么提高"**：32K 日常速度**没有任何提高**（纯负）；它的价值是**显存再分配**——在 80K–128K 基线 KV 溢出的降级死区，用 `16≤N≤24` 层 FFN 上 CPU 换回 **1.3–1.8 倍速度且 shared 归零**，prefill 不受损、能力零损失。

### 7.4 选型建议

| 需求 | 推荐配置 | 速度 | 可用上下文 |
|---|---|---|---|
| **短上下文 / 省显存** | `-ngl 99 -c 65536 q4_0`（b10883 复核） | ~33 t/s | 64K |
| **长上下文（80K–96K）** | `-ngl 99 -c 81920/98304 q4_0 -ncffn 16/24` | 14–19 t/s | 80K–96K（救援区） |
| **超长上下文（128K，批量）** | `-ngl 99 -c 131072 q4_0 -ncffn 24` | ~15.8 t/s | 128K（非交互） |

**选型不变**：需要 ≥64K 长上下文交互场景，本档 q4_0 `-ncffn` 救援方案仅覆盖至 96K 可用（128K 仅限非交互批量）；更高吞吐/更长上下文需求请参见 MoE 35B 系列单模型报告。`-ncffn` 只是把 27B 在 12GB 卡上的**溢出死区变成了有税可用区**（80K +79%、96K +27%，税 = decode 速度封顶在 CPU plateau 14–19 t/s）。
