# Qwen3.8-27B（qwen35 稠密混合 SSM，10.18GB IQ3\_XXS）

> 拆分自《本地模型调优全历程终版存档》，编号保留原章节号（§N.x）以便交叉引用；测量方法论见 [../llm-experiment-design/SKILL.md](../llm-experiment-design/SKILL.md)。

> 关键判定：**dense（非 MoE）**——`qwen35` 架构，65 层，`expert_count=0`，混合 SSM+注意力，`full_attention_interval=4` → 16 个 KV 层。原生 ctx 262144。

### 5.1 模型特性与 KV 容量

| 特性       | 值                                                |
| -------- | ------------------------------------------------ |
| 层数       | 65（每层 \~160MB）                                   |
| 注意力      | 24 query / 4 KV，key/val=256，KV 层=16              |
| 思考模式     | `enable_thinking` + `reasoning_effort`（默认 xhigh） |
| KV/token | f16=65536B；q8\_0=32768B；q4\_0≈16384B             |

→ 32K q8\_0 ≈ 1GB；权重 10.18GB 加载后 ded≈11.7GB → **只剩 \~0.3GB 给 KV → 32K 已临界**。

### 5.2 上下文断崖（-ngl 99 全 GPU）

| C       | q8\_0 shared | q8\_0 t/s | q4\_0 shared | q4\_0 t/s |
| ------- | ------------ | --------- | ------------ | --------- |
| **32K** | 277          | **24.5**  | 161          | **33.7**  |
| **48K** | 741          | **10.4**  | 242          | 26.3      |
| 64K     | —            | —         | 305          | 22.2      |
| 80K     | —            | —         | 700          | 14.6 ❌    |
| 96K     | —            | —         | 831          | 10.4 ❌    |

→ **dense 32K → 48K 是断崖**（q8\_0 t/s 减半、shared 暴涨）。根因：稠密权重占满显存，无 MoE 专家可卸载腾给 KV。**q4\_0 把断崖推后到 48K**（48K 仍 26.3 vs q8\_0 的 10.4），但未达理论 \~78K（权重占满 + SSM 状态开销）。**实际最佳上下文 = 32K**（q4\_0 33.7 t/s，shared 161MB）。
> **⚠️ 已勘误（见 §0 表与 §9.2）**：b10883 同会话干净重测显示 **64K@N=0 无损（33.3 t/s、shared 242）**，真断崖带在 **64K↔80K**（80K=10.4、shared 897⚠️），非 48K。本节 48K/64K 旧值疑受当时会话负载影响，跨代对比以 §9.2 为准；32K 值两代一致。

### 5.4 -ngl 真卸载（32K，q8\_0）——不划算

| -ngl | GPU 层 | ded   | t/s      |
| ---- | ----- | ----- | -------- |
| 99   | 65/65 | 11774 | **29.3** |

→ 稠密每 token 读所有层，卸载层走 CPU 代价极高（省 0.6GB t/s 腰斩）。早前 `-ngl 90/95` 均 ≥65 层=假卸载（全层仍上 GPU）无差异。

### 5.5 MTP / reasoning\_effort

- **MTP 不推荐**：GPU 已 86%→98% 饱和，draft-mtp 反而更慢（29.5→17.6），shared 顶到 1271MB。
- **reasoning\_effort**：`medium` 思考 563 字符 vs default 1692，答案仍正确（需 server 启动参数，本 build 不接受请求级字段）。

### 5.6 能力验证（32K 最终配置）

多步规划 100%、工具调用编排 100%、LRU 缓存 PASS、有效括号 PASS。能力优秀。

### 5.7 推荐配置

## 9. 新参数 `--n-cpu-ffn`（`-ncffn`）实测：27B IQ3\_XXS（b10883）

> **参数语义**（[PR #26622](https://github.com/ggml-org/llama.cpp/pull/26622)，b10883 可用，本地 build 10883/commit 91f6a6cf3 经 `--help` 确认）：`-ncffn N` 把**前 N 层的 dense FFN 权重**（`blk.0..N-1.ffn_up/down/gate`）留在 CPU 内存（tensor 级 buft override），attention/SSM/norm 仍按 `-ngl 99` 在 GPU——即 `--n-cpu-moe`（MoE 专家版）的 **dense 对应物**。**张量名命中验证**：qwen35 的 195/195 FFN 张量全部命中 regex（`gguf_ffn_probe.ps1`，两个量化档皆命中）→ 机制在此模型真实生效。测量全部在干净环境同会话完成（每点四件套：t/s + ded/shared + GPU util + CPU util）。

### 9.1 32K 纯吞吐：`-ncffn` **不是提速参数**（dense 上纯负）

| -ncffn N | idle ded | 腾出显存 | short t/s | GPU% | CPU% |
| ---- | ------ | ---- | --------- | ---- | ---- |
| 0 | 11479 | — | **33.9/33.3**（多会话一致） | 90→87 | 12→10 |
| 8 | 10875 | −604MB | 23.5/23.5 | 59 | **89** |
| 16 | 10360 | −1119MB | 18.0/18.1 | 50 | **100** |
| 24 | 9702 | −1777MB | 14.2/14.2 | 42 | 100 |
| 32 | 8913 | −2566MB | 11.4/11.3 | 31 | 100 |
| 48 | 7317 | −4162MB | 7.4/7.3 | 33 | 100 |

→ 每层 FFN 卸载释放 **≈75MB** 显存，但 **N=8 就已把瓶颈从 GPU 推到 CPU**（dense FFN 每 token 必经、矩阵×向量纯权重带宽 bound，20 线程 89% 饱和），t/s 单调腰斩：33→23.5→18→14→11→7。与 MoE `-ncmoe` 的本质区别：MoE 专家仅激活时才算、dense FFN 全量每 token 必算——**这就是报告 §5.4 "dense 卸载不划算"结论的参数化版本**（比 `-ngl` 整层卸载温和，但方向相同）。

### 9.2 ★唯一真实价值：大上下文"溢出救援"（顺带勘误断崖地图）

同会话先重扫基线：**b10883 干净环境下 64K@N=0 已无恙（33.3 t/s、shared 242）**→ 旧 §5.2"48K 断崖"修正为 **断崖带 64K↔80K**。在此新地图上：

| ctx | N=0（基线） | 救援配置 | 救援后 | Δ |
| ---- | ---------- | -------- | ------ | --- |
| 64K | **33.3**，shared 242 无溢出 | （不需要） | — | 用 -ncffn 反而自伤（N=16→17.7） |
| 80K | **10.4 ⚠️** shared 897 | **`-ncffn 16`** | **18.6**，shared 193 | **+79%** 且溢出清零 |
| 96K | **11.1 ⚠️** shared 1092 | **`-ncffn 24`** | **14.1**，shared 210 | **+27%** 且溢出清零 |
| 128K | 14.5 ⚠️ **shared 2026**（2GB 溢出） | `-ncffn 24` | 15.8，shared 234 | 速度持平、**2GB 溢出清零**（去 WDDM 分页风险） |

**深填充可用性**（判"能用"，非只"装下"）：80K@N=16 填 60.9K tokens **WALL 78.4s**（prefill **911.8 pps**、eval 17.2）✅；96K@N=24 填 73.9K **WALL 108.7s**（prefill 786.3、eval 13.6）✅。
→ **关键机制**：ncffn 的 CPU 瓶颈**只在 decode**（矩阵×向量、权重带宽 bound）；**prefill 是矩阵×矩阵，权重读取被 batch 摊薄，几乎不掉速**（912/786 pps ≈ 全 GPU 基线的 950-1120）——"能装下"与"能用"在救援点同时成立。128K 按 \~800pps 估算填 120K 需 \~150s+，仅适合非交互批量场景（未实测墙钟）。

### 9.3 ×MTP 交互：plateau 有回升，但**不叠加**（12GB 卡）

| 配置（MTP n=2） | plateau short | vs 无 MTP | 接受率 | shared |
| ---- | ---- | ---- | ---- | ---- |
| 80K N=16 | 21.9/22.2 | +18% | 63.8% | **804 ⚠️ 回溢出区** |
| 96K N=24 | 15.5/14.7 | +7% | 63.2% | 576 ⚠️ |
| 128K N=24 | 15.8/15.0 | ≈0 | 62.0% | 1536 ⚠️ |
| 32K N=24 | 14.6/15.1 | ≈0 | 60.2% | 192 ✅ |

→ MTP 批量验证确实摊薄了 CPU FFN 的单 token 权重成本（接受率 60-64% 健康、80K 点 +18%），**但 MTP 自身 draft 缓冲 +0.6\~1.1GB 把 ncffn 刚腾出的余量吃回**，shared 重新跳升 → 两个省/花显存的机制互相抵消，救援目标（零溢出）被破坏。**12GB 卡上二者只选一个；IQ3_XXS 救援场景选纯 -ncffn。**

### 9.4 能力：采样下**零损失**；但 temp=0 贪心跨后端**非位一致**

* **贪心对照**（temp=0）：N=24 从第 8 字符即与 N=0 分叉，一道 4 步算术链一次答错（2808 vs 正确 2534）。同配置自复现 100% 一致 → 分叉源于 **CUDA vs ggml-CPU 浮点累加顺序不同**（权重未变，≠量化降精度），贪心 argmax 把末位噪声级联放大。
* **客观判分**（temp 0.6 × 3 题 × 3 次，reference 程序生成标准答案）：**N=0 = N=16 = N=24 = 9/9（100%）** → **真实采样下能力无损**。
* 实操含义：依赖 temp=0 跨配置严格复现输出的场景（回归测试/快照比对）不要混用 ncffn 开关；常规使用不受影响。

### 9.5 推荐配置（IQ3_XXS @ b10883，更新 §5.7）

```
≤64K（默认，速度最优）:   -ngl 99 -c 65536 q4_0            → 33 t/s（b10883 复核 64K 无需卸载）
80K:                    -ngl 99 -c 81920  q4_0 -ncffn 16  → 18.6 t/s / wall 78s，零溢出
96K:                    -ngl 99 -c 98304  q4_0 -ncffn 24  → 14.1 t/s / wall 109s，零溢出
128K:                   -ngl 99 -c 131072 q4_0 -ncffn 24  → 15.8 t/s，零溢出（填 120K 墙钟长，非交互向）
（其余固定参数同 §1；-ncffn 与 MTP 不叠加；N 不必整除，救援点按"溢出多少补多少"选最小 N）
```

**选型不变**：需要 ≥64K 长上下文仍首选 MoE 35B（62-66 t/s 无断崖）；`-ncffn` 只是把 27B 在 12GB 卡上的**溢出死区变成了有税可用区**（80K +79%、96K +27%），税 = decode 速度封顶在 CPU plateau（14\~19 t/s）。Q2_K_XL 未测（本轮范围 IQ3_XXS）：其基线断崖在 96K/112K（MTP 64K），预期 -ncffn 正收益区间更靠后、幅度存疑，待后续补测。

**一句话回答"这个参数对 27B 有什么提高"**：32K 日常速度**没有任何提高**（纯负）；它的价值是**显存再分配**——在 80K\~128K 基线 KV 溢出崩盘的死区，用 `16≤N≤24` 层 FFN 上 CPU 换回 **1.3\~1.8 倍速度且 shared 归零**，prefill 不受损、能力零损失。
